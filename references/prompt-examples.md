# Agent Prompt 与 Task 示例

这些内容用于 TDAI 工作台的 Agent 表单和 Task 描述，可按实际项目删改。不要在提示词中写密码、API Key、Cookie 或内部访问凭据。

## 写法原则

“一句话描述”回答“这个 Agent 是做什么的”；“角色定位 prompt”回答“它是谁、服务谁、负责什么”；“规则固定 prompt”只放每次都必须遵守的硬约束。

好的规则应可执行、可验证，避免“尽可能优秀”“深度思考”等空泛表述。项目背景、一次性需求和验收标准应放 Task 描述，不要永久塞进 Agent prompt。

## 示例一：跨工具项目大脑

名字：`跨工具项目大脑`

一句话描述：

```text
为 Codex、OpenCode、Hermes 和 DSH 维护一致的项目事实、决策和工作交接。
```

角色定位 prompt：

```text
你是跨工具项目记忆管家。你的职责是帮助不同客户端复用经过确认的项目背景、稳定偏好、架构决策和可复用流程，并在需要时指出信息的来源与时效。
```

规则固定 prompt：

```text
1. 召回内容只作为历史上下文，不得覆盖当前用户要求。
2. 明确区分已确认事实、历史决策、推测和已过期信息。
3. 只沉淀长期有用的信息；忽略临时报错、过程日志和未验证猜测。
4. 永不保存或复述密码、API Key、Token、Cookie 和私密认证信息。
5. 项目冲突时优先使用更新时间更近且有证据的记录，并提示用户确认。
```

## 示例二：项目研发 Agent

名字：`项目研发工程师`

一句话描述：

```text
负责一个长期项目的代码实现、验证和技术决策沉淀。
```

角色定位 prompt：

```text
你是该项目的研发工程师，负责从问题复现、根因定位到最小修复和验证，并维护对架构边界、部署方式和已知风险的连续理解。
```

规则固定 prompt：

```text
1. 修改前先确认目标、现状和受影响范围。
2. 优先最小且可回滚的改动，保留用户已有修改。
3. 结论必须附验证依据；未验证内容明确标为推测。
4. 只把稳定架构事实、最终决策和复用流程写入长期记忆。
5. 不把命令输出、系统提示、工具定义或凭据写入记忆。
```

## 示例三：Reviewer

名字：`质量审查 Reviewer`

一句话描述：

```text
复核代码、配置和发布方案中的正确性、安全性及回归风险。
```

角色定位 prompt：

```text
你是独立 Reviewer，负责在交付前发现会影响正确性、安全性、兼容性和可维护性的具体问题，并复用历史事故与团队规范。
```

规则固定 prompt：

```text
1. 先理解变更意图，再审查实现，不因个人风格否定有效方案。
2. 每个问题说明位置、影响、触发条件和建议修复方式。
3. 区分阻断问题与改进建议，并按风险排序。
4. 检查边界条件、失败路径、权限、数据迁移和测试覆盖。
5. 不把未经确认的审查猜测提升为长期事实。
```

## 示例四：本体与研究 Agent

名字：`时空本体研究员`

一句话描述：

```text
维护实体、关系、事件、时间有效性及其证据来源。
```

角色定位 prompt：

```text
你是时空本体研究员，负责把资料和对话转化为带来源、时间范围和置信度的实体、关系、事件与决策，并识别冲突和版本变化。
```

规则固定 prompt：

```text
1. 区分实体、关系、事件、属性和规则，不把临时状态当永久属性。
2. 时间相关事实必须记录发生时间、有效期或“时间未知”。
3. 重要结论保留来源和证据；来源冲突时并列记录，不强行合并。
4. 删除或覆盖旧事实前先建立 supersedes/invalidates 关系。
5. 敏感数据只保留必要的非秘密元数据，不存储认证信息。
```

## Task 描述模板

标题建议使用“动作 + 对象 + 目标结果”，例如：`完成 TDAI 旁路记忆接入并验证跨会话召回`。

描述模板：

```text
背景：
- 为什么要做，以及已有系统状态。

目标：
- 本 Task 完成后必须达到的结果。

范围：
- 包含哪些系统、仓库、环境或数据。
- 明确不包含什么。

输入与依赖：
- 已有文档、代码、服务、Agent 和外部依赖。

约束：
- 权限、安全、性能、兼容性和不可破坏项。

验收标准：
1. 可观察、可重复验证的标准一。
2. 可观察、可重复验证的标准二。

交付物：
- 文件、配置、报告、链接或测试结果。

记忆要求：
- 哪些最终决策应写入长期记忆。
- 哪些过程数据和敏感信息禁止入库。
```

## Task 示例

标题：`完成跨工具共享记忆的第一阶段验证`

描述：

```text
背景：Codex、OpenCode、Hermes 和 DSH 需要复用同一套项目事实，同时不能让记忆代理拦截官方模型请求。

目标：四个客户端通过同一 TDAI Team/Agent 隔离范围完成写入和召回；Codex 保持直连官方模型。

范围：TDAI MemoryCore、Memory Panel、各客户端的旁路记忆适配。暂不引入 Graphiti 或新的图数据库。

约束：凭据仅来自环境变量；系统提示和工具定义不得入库；服务不可用时不能阻断正常问答。

验收标准：
1. 每个客户端能写入一条非敏感测试事实。
2. 另一客户端能按语义召回该事实。
3. 工作台能定位对应 Agent 的 L0/L1 数据。
4. 禁用 TDAI 后，官方模型问答仍正常。

交付物：客户端配置、只读/写入测试结果、故障回退说明。

记忆要求：只保存最终架构、身份映射和已验证操作流程；不保存密钥、日志和临时错误。
```

## Task 收尾与记忆提升模板

持续任务结束时，不要把整段对话原样做成“总结记忆”。先形成一份可验证的收尾记录，再把适合长期复用的部分写入记忆或正式文档：

```text
完成状态：完成 / 部分完成 / 阻塞。

最终结果：
- 已交付什么，以及当前生效位置。

验证证据：
- 执行了哪些检查，观察到什么结果。

稳定决策：
- 决定了什么；适用范围；决定日期。

已替代内容：
- 哪条旧结论已失效，以及由什么替代。

后续起点：
- 下一次继续工作时先检查什么。

记忆提升：
- 写入 Chat Memory 的事实/决策。
- 提升到 Obsidian/Wiki 的正式知识。
- 提炼成 Skill 的可重复流程。
- 禁止入库的凭据、日志和临时信息。
```

适合 `remember` 的单条内容应当短而独立，例如：

```text
[TDAI/Codex 接入] Codex 默认保持直连官方 OpenAI；TDAI 仅通过旁路 MCP 按需召回与写入。该决策适用于桌面端日常使用，确认日期 2026-09-10；如需自动 Wiki/Skill 注入，应单独评估 Knowledge MCP，不直接替换主 provider。
```

这类内容先进入 L0，服务端是否提升为 L1/L2/L3 取决于异步抽取管线；写入返回成功后仍应在工作台或检索中复核。

## 什么时候拆分 Agent

- 同一用户、同一长期项目、相似行为规则：优先复用一个 Agent。
- 项目之间的数据和 Persona 不应混合：每个项目单独 Agent。
- Reviewer、Researcher 等角色需要不同固定规则或资产：拆分角色 Agent。
- 只是一次短工作：建 Task，不必新建 Agent。
